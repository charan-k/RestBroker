# Implementation Plan

## Status and scope

This plan replaces the stale T1–T6 public-UI plan. T1–T3 below are already completed and are recorded for traceability; they are not work to repeat.

The approved scope is:
- API suite targeting the public `https://restful-booker.herokuapp.com` service, including CRUD, create, and delete coverage.
- UI CI using a private, per-run environment based on the official `mwinteringham/restful-booker-platform` source pinned to `d36bd3f8647a091d406e53bad463c5e3e5d2ece1`.
- CI runs API and UI suites in parallel. UI provisioning must precede UI tests; provisioning/readiness failure must fail with diagnostics; teardown must run after success or failure.
- AC26 requires overlapping runs to remain isolated and avoid process collisions.

No shared public UI mutations or fallback to the public UI are in scope. D1's provisioning approach is approved and recorded below. Implementation of provisioning, browser tests, lifecycle orchestration, and live public API mutations remains blocked on their outstanding decisions and approval gates.

## Unresolved information

The following remain **Not Found** and must be resolved in the applicable decision tasks before dependent implementation begins:

- Docker Engine/Compose availability on the selected runner and exact safe provisioning commands.
- Runtime-only Compose override details and verification that all upstream fixed host mappings are removed except the dynamic frontend loopback port; runtime credentials.
- Probe image provenance/digest and private-network attachment mechanism for the approved short-lived probe container.
- Diagnostic artifact destination, quantitative bounds, implementation, and runtime verification of the approved sanitization policy.
- Docker Engine/Compose runner/plugin version and permissions, cancellation-safe post-step guarantees, and cleanup after abrupt runner loss or hard termination.
- Exact action/setup SHAs; workflow event/branch and GitHub Environment/reviewer configuration; exact secret names/scope.
- Mechanism to enforce the approved digest-pinning requirement against floating base-image references in the pinned upstream source.
- API credential authorization and availability, concrete serialization mechanism, external service stability/rate/reset/persistence behavior, marker storage field/entropy criterion, and handling of possible orphan records after uncertain creates or abrupt runner loss.
- Complexity estimates and exact approved requirement IDs.
